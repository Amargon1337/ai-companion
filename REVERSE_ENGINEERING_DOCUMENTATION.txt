================================================================================
1. PROJECT OVERVIEW
================================================================================

1.1 Purpose
───────────
This is a personal AI companion Telegram bot designed for a single user (Ivan).
The bot maintains long-term memory, builds a dynamic personality model, performs
causal reasoning, makes predictions, manages goals, executes Google-grounded
web search, and adapts its conversational style through a policy layer.

1.2 Bot Type
────────────
- Single-user private Telegram bot
- Uses aiogram 3.x for Telegram interaction
- Uses Google Gemini API (gemini-3.1-flash-lite for chat, gemini-2.5-flash for
  search with grounding) as the LLM backend
- Memory-backed with SQLite primary store + JSONL append-only audit logs
- Runs as a long-lived Python process (asyncio event loop)

1.3 Core Capabilities
─────────────────────
- Long-term memory via fact extraction, consolidation, reflection generation
- Personality modeling with interests, values, beliefs, fears, motivations
- Goal management (CRUD + tracking)
- Causal reasoning engine (cause-effect links between events)
- Prediction engine (hypothesis tracking with verification/falsification)
- World model (active contexts, recent patterns)
- Google Search with grounding (personalized web search)
- Intent routing (natural language commands like "запомни...", "моя цель...")
- Self-critique (confidence scoring, warning flags, uncertainty detection)
- Policy layer (adaptive response mode based on detected user state)
- Mood detection (heuristic-based emotional state inference from text)
- Importance scoring and decay for facts
- Rate limiting, circuit breakers for background tasks
- TikTok downloading / voice recognition / document processing / media handling
- Monthbook generation (monthly autobiographical chapter assembly)
- Retrospective analysis (30-day change detection)
- Self-model introspection (bot knows its own strengths, weaknesses, domains)

1.4 Architecture Philosophy
───────────────────────────
The architecture follows a "memory-first" design with these principles:
- NEVER DELETE — facts are archived/inactivated, never removed
- Dual-write: SQLite (ACID primary) + JSONL (append-only audit trail)
- Retrieval-augmented generation (RAG) via RetrievalBudgetManager
- Modular pipeline: compress → extract facts → consolidate → reflect → personality
- Background processing for non-critical updates (personality, reflections)
- Circuit breakers prevent cascading failures in background tasks
- Self-critique with grounding fallback for uncertain factual responses

1.5 Current Maturity Level
──────────────────────────
Classification: BETA / EARLY PRODUCTION
- Core pipeline works and is tested (3 test files, conftest with fixtures)
- Many dead .pyc caches from removed modules indicate significant refactoring
- Data corruption in JSONL files (encoding issues visible in beliefs, goals,
  causal_links — garbled text suggests UTF-8/CP1251 mismatch)
- Security tokens are HARDCODED in api.env (included in repo!)
- No separation of concerns between bot_core.py (~561 lines) and services
- user_model.py has mostly stub implementations
- Several stale .pyc files from deleted modules (autonomous_reasoning,
  background_workers, conflict_detection, embeddings, etc.)
- No CI/CD, no Docker, no health checks, no metrics
- Single-user hardcoded via ADMIN_IDS

4. MESSAGE PROCESSING PIPELINE
================================================================================

4.1 Complete Lifecycle — Step by Step
──────────────────────────────────────

STEP 1: TELEGRAM UPDATE
   File: companion/main.py
   Function: run()
   └─ dp.start_polling(bot, handle_as_tasks=True)

STEP 2: AUTH MIDDLEWARE
   File: companion/main.py:28-35
   Class: AuthMiddleware.__call__()
   └─ Checks event.from_user.id in ADMIN_IDS
   └─ If NOT admin → "Пошёл нахуй, ты не Иван. Доступ закрыт." → RETURN

STEP 3: HANDLER DISPATCH
   Priority order (from companion/handlers/chat.py):
   1. /start command → cmd_start()
   2. /help command → cmd_help()
   3. /summary or /summarize command → cmd_summary() → report_service.show_summary()
   4. /personality command → cmd_personality() → report_service.show_personality()
   5. /remember command → cmd_remember() → memory_service.remember_text()
   6. /search command → cmd_search() → web search with grounding
   7. Text messages (F.text & ~F.text.startswith("/") & ~F.text.contains("tiktok.com"))
      → text_handler()
   8. TikTok URLs (F.text & F.text.contains("tiktok.com"))
      → tiktok_handler() → yt-dlp download → Gemini vision → process_llm_request()

STEP 4: TEXT HANDLER (chat.py:113-122)
   Function: text_handler()
   1. Check LegacyStorage.parse_remember_command() — "запомни ..." prefix
   2. If match → memory_service.remember_text() → RETURN
   3. Check try_handle_intent() — NL intent router (intents.py)
   4. If any intent matched → RETURN
   5. If no intent → core.process_llm_request(message, text)

STEP 5: process_llm_request() (bot_core.py:242-250)
   └─ Calls build_context() to prepare all data

STEP 6: build_context() (bot_core.py:196-239) — THE CENTRAL ORCHESTRATOR
   a. Extract query from payload
   b. check_rate_limit() — max 10 req/min per user
   c. Create RuntimeState
   d. score_message_importance() — heuristic 1-10
   e. infer_mood_lite() — anxiety/anger/sadness/energy
   f. memory_store.log_message() — save message to SQLite + JSONL
   g. reasoning_engine.auto_reasoning_context() — update world model, capture goals/predictions
   h. memory_service.auto_add_event_from_message() — if importance >= 8
   i. classify_intent() — memory | world | mixed
   j. _get_policy_decision() — detect user state + decide response policy
   k. _load_retrieval_context() — gather facts, reflections, summaries, etc.
   l. If intent is "world" or "mixed" with confidence >= 0.55:
      → _handle_grounding() → search_with_grounding() → send → RETURN
   m. Session management: create or reuse user_chats[uid]
   n. Increment message counter
   o. Background tasks: every 10 messages → _background_personality_micro_update()
   p. If counter >= SUMMARY_THRESHOLD (50) → compress_and_reset()
   q. Return context dict

STEP 7: _generate_and_send_response() (bot_core.py:331-379)
   a. RetrievalBudgetManager.select() — build ranked context bundle
   b. ContextBundle.to_prompt_block() — format as text block
   c. _build_user_prompt_block() — add reasoning hints if causal/future query
   d. policy_layer.format_prompt_with_policy() — if policy constraints exist
   e. send_typing() — Telegram typing indicator
   f. chat.send_message(content_payload) — LLM call (with timeout + retry)
   g. policy_layer.enforce_constraints() — post-process for question limits
   h. self_model.critique_response() — self-critique
   i. _apply_critique_to_text() — augment response with uncertainty markers
   j. If confidence < 0.55 and factual query → _grounding_answer_only()
   k. send_long_message() — split by sentence boundaries if > 4000 chars
   l. memory_store.log_message(assistant) — save response
   m. If importance >= 7 and cooldown passed → _background_user_model_reflection()

4.2 Branching Points
─────────────────────
1. AUTH → non-admin users rejected immediately
2. COMMAND vs TEXT vs TIKTOK → router based on message properties
3. INTENT MATCH → if NL command matched, service handles and RETURNS
4. GROUNDING → if world/mixed intent, search with grounding and RETURNS
5. COMPRESSION → if counter >= 50, compress and reset context
6. SELF-CRITIQUE → low confidence triggers grounding fallback
7. MEDIA TYPES → voice/document/photo/video have dedicated handlers

4.3 Exception Handling
──────────────────────
- LLM errors → caught in process_llm_request() → "API ошибка: {e}"
- Grounding errors → "⚠️ Google Search недоступен. Отвечаю из личной памяти..."
- Media errors → caught per-handler → "Ошибка: {e}"
- JSON parse errors → logged, empty default returned
- Background task errors → logged, circuit breaker, self_model.log_error()
- Compress failures → retry 2x, reduce counter by 25, log error
- Foreign key / DB errors → SQLite constraints

4.4 Fallback Mechanisms
───────────────────────
- No session → create_default_session() with history reconstruction from SQLite
- Empty LLM response → retry in compress, error message to user
- Grounding fails → fall back to normal chat response
- Self-critique low confidence → grounding retry
- Personality load fails → EMPTY_PERSONALITY dict
- JSON parse fails → try markdown code block extraction → empty fallback
- Document unreadable → upload raw to Gemini
- File encoding detection → try utf-8, utf-8-sig, cp1251, latin-1

5.2 Detailed Memory Types
─────────────────────────

5.2.1 FACTS (memory/store.py, models.py:20-48)
───────────────────────────────────────────────
Structure: Fact dataclass
  - id: str = "fact_YYYYMMDD_XXXXXXXX"
  - fact: str — text of the fact
  - date: str — YYYY-MM-DD
  - created_at: str — ISO datetime
  - memory_kind: "permanent" | "state" | "event"
  - importance: int 1-10
  - confidence: float 0.0-1.0
  - source: str — e.g., "summary_20260623"
  - source_type: str — "compress" | "user" | "auto_event"
  - tags: list[str] — ["anchor", "core_identity", "pinned", "permanent", ...]
  - status: "active" | "superseded" | "inactive" | "archived"
  - valid_from: str
  - schema_version: int

Creation: 
  - extract_facts() at compress (llm/pipeline.py:24-86)
  - fact_from_permanent_note() for /remember
  - auto_add_event_from_message() for high-importance events
  - LLM parses conversation summary + recent messages → JSON array

Status Lifecycle:
  - active → (supersedes relation) → superseded
  - active → (age > 90d, importance ≤ 3) → inactive
  - active → (age > 180d, importance ≤ 4) → archived
  - permanent facts NEVER decay

5.2.2 MESSAGES (models.py:76-99)
─────────────────────────────────
Structure: MessageRecord dataclass
  - id: str = "msg_YYYYMMDD_XXXXXXXX"
  - role: "user" | "assistant"
  - text: str — message content (assistant responses truncated to 500 chars)
  - importance: int 1-10
  - mode: str — "default" | "search" | "compress"
  - signals: list[str] — ["long", "memory_query", "emphasis", "named_entity"]
  - ts: str — ISO datetime
  - user_id: int | None

Logging:
  - Every user message → log_message() in build_context()
  - Every assistant response → log_message() in _generate_and_send_response()
  - Dual write: SQLite + JSONL

5.2.3 REFLECTIONS (models.py:102-125)
──────────────────────────────────────
Structure: Reflection dataclass
  - id: str = "refl_YYYYMMDD_XXXXXXXX"
  - insight: str — generalized observation
  - based_on: list[str] — fact IDs that informed this reflection
  - period: str — "YYYY-MM"
  - importance: int 1-10
  - confidence: float 0.0-1.0
  - status: "active" | "superseded" | "inactive" | "archived"

Creation:
  - generate_reflections() every REFLECTION_EVERY_N (4) compress cycles
  - LLM analyzes facts + summary for the period

5.2.4 BELIEFS (memory/store.py:147-162)
────────────────────────────────────────
Structure: dict
  - id: str = "belief_XXXXXXXXXX"
  - belief: str — extracted belief
  - based_on: list[str] — sources
  - importance: int (default 6)
  - status: "active"
  - created_at: str — ISO datetime

Creation:
  - generate_personality_snapshot() syncs beliefs from personality model

5.2.5 PERSONALITY (memory/store.py:164-199)
────────────────────────────────────────────
Structure: dict (EMPTY_PERSONALITY template)
  - interests: dict[str, int] — topic → weight 1-10
  - beliefs: list[str]
  - values: list[str]

6.4 Dual-Write Architecture
────────────────────────────
The system uses a DUAL-WRITE strategy:
1. SQLite is written FIRST (ACID guarantee)
2. JSONL is written SECOND (append-only audit log)
3. On startup, _migrate_jsonl_if_empty() checks if SQLite is empty and loads

This means:
- SQLite is the primary operational store
- JSONL provides append-only audit trail and crash recovery
- Both are written for every operation (log_message, add_fact, add_reflection)
- JSONL rotation preserves backup history

7.1 RetrievalBudgetManager (memory/retrieval.py)
─────────────────────────────────────────────────
Class: RetrievalBudgetManager
Configuration:

  - RETRIEVAL_MAX_FACTS = 25
  - RETRIEVAL_MAX_REFLECTIONS = 5

7.2 select() Algorithm
───────────────────────
Input: query, facts[], reflections[], summaries[], permanent_notes, 
       personality_snapshot, recent_messages, active_goals, causal_links,
       predictions, world_model_context

Step 1: FILTER ACTIVE FACTS
  - Exclude inactive facts; optionally include archived

Step 2: EXTRACT PINNED FACTS (extract_pinned_facts)
  - Tags: "pinned", "core_identity", "anchor"
  - memory_kind == "permanent"
  - importance >= 9
  - Limited to top 5 by importance (sorted)
  - These bypass relevance scoring — always included

Step 3: COMPUTE MOOD (once per query)
  - infer_mood_lite() if query >= 3 words
  - Used for mood-aware boosting

Step 4: SCORE REGULAR FACTS
  - _ranked_score(f) = retrieval_score(f, query) + mood_to_retrieval_boost(mood, f)
  - retrieval_score() combines:
    - Importance (weight 0.4)
    - Recency (weight 0.25) — exponential decay with half-life (45d state, 120d event)
    - Relevance (weight 0.35) — keyword overlap + tag match
  - mood_to_retrieval_boost() adds 0.0-0.3 based on mood state:
    - High anxiety → anchor/coping facts +0.3
    - High sadness → positive facts +0.25
    - High anger → trigger/solution facts +0.2
    - Low energy → energy management facts +0.2

Step 5: MERGE PINNED + RANKED REGULAR
  - available_slots = max_facts - len(pinned)
  - ranked_facts = pinned + ranked_regular[:available_slots]

Step 6: RANK REFLECTIONS
  - Active reflections only
  - Sort by: importance/10 + (0.5 if query in insight)
  - Limit to max_reflections (5)

Step 7: ASSEMBLE SUMMARY STACK (3-tier)
  - Tier 1: Last summary (always, truncated to 1500 chars)
  - Tier 2: Up to 3 keyword-matched summaries (truncated to 1200 chars)
  - Tier 3: Master summary (added in sessions.py, not retrieval)

Step 8: ADD RECENT IMPORTANT MESSAGES
  - Last 7 user messages with importance >= 6
  - Formatted as "[{ts}] {text[:200]}"

Step 9: BUILD CONTEXT BUNDLE
  - ContextBundle dataclass with all fields
  - Each field trimmed:
    - permanent_notes[:800]
    - world_model_context[:1200]
    - active_goals[:5], causal_links[:5], predictions[:5]

Step 10: TRIM TO BUDGET (char_budget = 4000)
  - While prompt_block > budget:
    - Pop facts from end (lowest ranked)
    - Pop summaries from end
    - Pop reflections from end

7.3 Scoring Function (memory/importance.py:57-92)
──────────────────────────────────────────────────
retrieval_score() formula:
  score = 0.4 * (importance/10) + 0.25 * decay_factor + 0.35 * relevance

Where:
  - decay_factor = exp(-0.693 * days / half_life) for non-permanent
  - permanent = 1.0 (no decay)
  - state half_life = 45 days
  - event half_life = 120 days
  - relevance = keyword overlap (0.3-1.0) + tag hit bonus

10. SELF CRITIQUE SYSTEM
================================================================================

10.1 Overview
─────────────
The self-critique system evaluates LLM responses before sending to the user.
It is implemented in two locations:
  1. self_model.py — SelfModel.critique_response() (the critic)
  2. bot_core.py — _run_self_critique() + _apply_critique_to_text() (runtime)

10.2 Critique Algorithm (self_model.py:156-194)
────────────────────────────────────────────────
Input: response, query, context (facts_count, has_causal, has_predictions)

Checks performed:
  1. UNCERTAIN LANGUAGE — if response contains "возможно", "наверное", "думаю что"
     → flag: "uncertain_language"
     → max reduction: 0.2

  2. FACTUAL ASSERTION WITHOUT SOURCE — if query has factual triggers (когда, где,
     сколько, кто) and response has no sources and no "Не уверен"
     → warning: "Фактическое утверждение без источника"
     → max reduction: 0.3

  3. DOMAIN COMPETENCE — if query contains a domain name and bot's confidence
     for that domain is < 0.5
     → warning: "Низкая компетентность в домене '{domain}' ({conf:.0%})"
     → max reduction: 1.0 - confidence

Confidence formula: 1.0 - max_reduction (MAXIMUM reduction, not cumulative)
Initial confidence: 1.0

10.3 Runtime Integration (bot_core.py:494-536)
───────────────────────────────────────────────
_run_self_critique():
  - Wraps self_model.critique_response() with try/except
  - Falls back to {"flags": [], "confidence": 1.0, "warnings": []}

_apply_critique_to_text():
  1. If confidence >= 0.75 AND no warnings → return text as-is
  2. If "uncertain_language" in flags AND warnings → append warnings
  3. If confidence < 0.55 → prefix: "Не до конца уверен, но по текущему контексту: "
  4. If confidence 0.55-0.75 → prefix: "Похоже, что: "
  5. Only adds prefix if text doesn't already start with uncertainty markers
  6. Appends warning suffix: "\n\n⚠️ Уровень уверенности снижен: ..."

10.4 Grounding Retry (bot_core.py:530-561)
──────────────────────────────────────────
_should_retry_with_grounding():
  - Checks if query matches factual pattern: /^(?:когда|где|кто|сколько|какая|какой)\b/
  - OR if any warning contains "источник"
  - Returns True → triggers _grounding_answer_only()

_grounding_answer_only():
  - Builds full retrieval context
  - Calls search_with_grounding()
  - Returns grounded answer with "🔍" prefix
  - If fails, returns empty string (original response preserved)

19.2 Fallback Strategies
────────────────────────
1. LLM fails → retry 3x with exponential backoff (2^attempt * 4s base)
2. Compress fails → retry 2x, reduce counter by 25, don't reset session
3. Grounding fails → fallback to normal chat response
4. Grounding retry fails → empty string → original response preserved
5. JSON parse fails → try markdown code block → empty default
6. Personality load fails → EMPTY_PERSONALITY dict
7. File encoding detection → try utf-8 → utf-8-sig → cp1251 → latin-1
8. Background task fails → circuit breaker (5 failures → 10min cooldown)
9. SQLite duplicate → INSERT OR IGNORE

──────────────────────────────
1. Gemini API outage → complete bot unavailability (no fallback LLM)
2. api.env missing → ValueError at import, crash on startup
3. SQLite corruption → complete data loss (no replica)
4. Personality.json corrupt → EMPTY_PERSONALITY (acceptable)
5. Background task pileup → semaphore(5) limit, but no timeout on queue
6. send_long_message() → no error handling if piece of the message fails

20. PERFORMANCE ANALYSIS
================================================================================

20.1 O(n) Operations
─────────────────────
1. MemoryStore.search_facts() — O(n) linear scan over ALL active facts
   - File: memory/store.py:92-104
   - For each query, scans every active fact for substring match
   - With 10K+ facts, this becomes slow

2. MemoryStore.find_similar_fact() — O(n) with text_overlap()
   - File: memory/store.py:117-127
   - Computes character n-grams for EVERY active fact
   - text_overlap() builds n-gram sets per comparison

3. MemoryStore.facts_for_period() — O(n) full scan
   - File: memory/store.py:203-209
   - No SQL WHERE clause — loads ALL facts, filters in Python

4. MemoryStore.apply_importance_decay() — O(n) full scan
   - File: memory/store.py:219-232
   - Iterates all active facts, checks age

5. ReasoningEngine.list_goals() — O(n) full file read
   - File: reasoning.py:342-361
   - Reads entire goals.jsonl, parses every line, sorts

6. ReasoningEngine.list_causal_links() — O(n) full file read
   - Same pattern as goals

7. ReasoningEngine.list_predictions() — O(n) full file read
   - Same pattern

8. RetrievalBudgetManager.select() — O(n log n) sort
   - File: memory/retrieval.py:58-73
   - Sorts all active facts by score

20.2 O(n²) Operations
──────────────────────
1. generate_personality_snapshot() with _merge_personality()
   - Dedup logic iterates all items in each list for normalization
   - Union operation is O(n*m) for lists with normalization

2. CONSOLIDATION_PROMPT processing
   - LLM processes full fact list, but LLM call itself is constant time
   - Prompt size grows with fact count

20.3 Heavy Database Queries
────────────────────────────
1. list_messages() — "SELECT * FROM messages WHERE importance>=? ORDER BY ts DESC"
   - No LIMIT by default in the SQL query (limit applied via Python)
   - ORDER BY ts DESC with no index on ts (only index on ts is for column, not used in ORDER BY)
   - Wait, there IS an index idx_messages_ts — so this is fine

2. list_facts() — "SELECT * FROM facts WHERE status=? ORDER BY date DESC, created_at DESC"
   - Uses idx_facts_status index, but ORDER BY date + created_at may be slow

3. No index on fact_relations.from_id or to_id
   - get_causal_chain() does DFS — each level does full table scan

20.4 Potential Memory Leaks
────────────────────────────
1. user_chats dict — never bounded, grows with each unique user (but single-user)
   - File: bot_core.py:37

2. user_message_counts — same pattern

3. _user_request_times — cleaned every 60s but stores all timestamps
   - File: bot_core.py:46,258

4. _background_task_failures — unbounded keys
   - File: bot_core.py:50

5. personality.json cache — MemoryStore._personality_cache
   - File: memory/store.py:32
   - Cached forever, never invalidated (manual reload)
   - PRO: no repeated reads
   - CON: stale data until reload

6. JSONL files — append-only, rotation only at 50MB/500k lines
   - messages.jsonl currently 942KB / 518 lines — fine
   - But will grow unbounded between rotations

20.5 Threading / Async Concerns
────────────────────────────────
- All LLM calls use asyncio.to_thread() — synchronous Gemini client in thread pool
- No asyncio timeout on to_thread itself (run_llm wraps with asyncio.wait_for)
- Background tasks use asyncio.create_task() with no await — fire-and-forget
- No task result tracking — errors "disappear" into the event loop

21. SECURITY ANALYSIS
================================================================================

21.1 CRITICAL: API Keys in Repository
─────────────────────────────────────
File: api.env (included, not gitignored)
Impact: LEAKED Telegram Bot API token + Google Gemini API key
Fix: Revoke both tokens immediately, add api.env to .gitignore

21.2 Race Conditions
─────────────────────
1. personality.json read/write without locking
   - _background_personality_micro_update() reads → modifies → writes
   - Meanwhile, generate_personality_snapshot() (in compress) does the same
   - Two concurrent writes can corrupt the file

2. todo.json read/write without locking
   - todo operations read → modify → write on todo.json
   - No file locking → concurrent operations lose data

3. JSONL append is atomic per write but:
   - Dual-write (SQLite + JSONL) is not transactional
   - If SQLite succeeds but JSONL fails → inconsistency

4. MemoryStore._personality_cache
   - Read in load_personality(), written in save_personality()
   - Not thread-safe (but LLM runs in thread pool)
   - Python GIL mitigates, but still a design risk

21.3 Shared State (Global Singletons)
──────────────────────────────────────
All global singletons are mutable:
  - memory_store (MemoryStore)
  - retrieval_mgr (RetrievalBudgetManager)
  - user_chats (dict[int, Any])
  - reasoning_engine (ReasoningEngine)
  - user_model (UserModel)
  - self_model (SelfModel)
  - policy_layer (PolicyLayer)

All background tasks access these shared objects without synchronization.
Python's GIL provides basic protection, but logical races exist.

21.4 Data Corruption Risks
───────────────────────────
1. JSONL files show mojibake (encoding corruption in existing data)
   - beliefs.jsonl, causal_links.jsonl, goals.jsonl, predictions.jsonl,
     messages.jsonl all show garbled text (UTF-8 encoded CP1251?)
   - This is pre-existing data damage, not active corruption

2. SQLite + JSONL dual-write drift:
   - No mechanism to reconcile differences
   - If one write fails, stores diverge permanently

3. Personality.json partial write:
   - Not atomic (json.dump to open file)
   - Crash during write → truncated/broken JSON

21.5 Prompt Injection Risks
───────────────────────────
1. User message → directly into LLM prompt
   - File: bot_core.py:350, llm/prompts.py prompts
   - SYSTEM_INSTRUCTION says "Разговаривай цинично..." — injection attempt
   - LLM could be tricked via user message

2. Document text → directly into LLM prompt
   - documents.py:91 — file content sent to LLM as-is
   - Injected instructions in uploaded documents would be executed

3. ivan.txt content → system instruction
   - Static persona appended to every system instruction
   - If modified, could inject instructions

4. Memory facts → system instruction (via retrieval)
   - RAG context includes facts extracted from user messages
   - Potential for self-reinforcing injection loops

21.6 Storage Risks
───────────────────
1. No encryption at rest for sensitive data
   - ivan.txt contains medical/psychological data
   - personality.json, beliefs.jsonl contain personal analysis
   - SQLite database is plaintext

2. No access control beyond Telegram AuthMiddleware
   - Anyone with file system access can read all data

3. Logging of sensitive data
   - bot.log may contain message content and API keys
   - self_errors.jsonl logs error contexts

21.7 Denial of Service
──────────────────────
1. Large document upload → MAX_DOCUMENT_CHARS (120K) limit exists
   - But Gemini file upload bypasses this for binary files
2. No attachment size limit on Telegram side
3. Background task semaphore (max 5) prevents OOM, but:
   - Tasks are never cancelled/timeouted
   - If all 5 slots blocked, new tasks pile up

WHAT IS THIS PROJECT?
─────────────────────
A single-user Telegram chatbot that acts as a personal AI companion with
long-term memory and personality modeling. It uses Google Gemini for LLM
capabilities and stores everything in SQLite + JSONL files.

KEY TECHNOLOGIES:
  - Python 3.11+ / asyncio
  - aiogram 3.x (Telegram Bot framework)
  - Google Gemini API (genai SDK)
  - SQLite (primary store)
  - JSONL (audit trail)
  - yt-dlp, pydub, SpeechRecognition, pypdf, python-docx (optional)

ARCHITECTURE HIGHLIGHTS:
  - Memory-first design: facts extracted from conversations every ~50 messages
  - Dual-write: SQLite (ACID) + JSONL (append-only) for every operation
  - Retrieval-Augmented Generation (RAG) with budget management (4000 chars)
  - Self-critique system with confidence scoring and automatic fallback
  - Policy layer adapts response style based on detected user state
  - Background tasks with circuit breakers and semaphore limits
  - JSONL rotation at 50MB / 500k lines
