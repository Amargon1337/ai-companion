# ЭТАП 1. АРХИТЕКТУРА

## Карта модулей и потоков

**Жизненный цикл сообщения:**

1. `handlers/chat.py` → `bot_core.process_llm_request()`
2. `build_context()`:

1. `analyze_message()` — **отдельный LLM-вызов** (gemini-3.1-flash-lite, structured output): intent, mood anxiety/anger/sadness/energy, user_state, importance 1–10, command
2. `memory_store.log_message()` → SQLite (санитизация)
3. `reasoning_engine.auto_reasoning_context()` — world model update, захват целей regex'ом («хочу…»), keyword-подбор causal links / predictions
4. `memory_service.auto_add_event_from_message()` — авто-событие при importance ≥ 8
5. `_load_retrieval_context()` — FAISS-поиск фактов + pinned/permanent merge, reflections, summaries, user_model block, **faiss_scores**
6. policy_layer → режим ответа по user_state
7. при `count >= 50` → `compress_and_reset()`



3. `_generate_and_send_response()`:

1. `retrieval_mgr.select(...)` собирает bundle **с faiss_scores и mood-boost**
2. **сессия пересоздаётся на каждый ход**; контекст инжектится через `build_system_instruction()`, который вызывает `retrieval.select()` **второй раз — уже без faiss_scores и без mood**
3. генерация (gemma-4-31b-it, fallback flash-lite) → policy enforce → self-critique (эвристики) → grounding-retry при confidence < 0.55
4. `_analyze_context_utilization()` — метрики sent/used по словесному оверлапу → SQLite
5. при importance ≥ 7 → фоновая `background_user_model_reflection()` (ещё 1–7 LLM-вызовов: рефлексия + shadow eval на каждую категорию)



4. Каждые 10 сообщений — `background_personality_micro_update()` (keyword-подсчёт интересов).


**Жизненный цикл воспоминания (compress-пайплайн):**
`SUMMARY_PROMPT` → summary в SQLite + vector → `extract_facts` (dedup через FAISS+n-gram, injection-карантин, авто-теги anchor/core_identity, авто-promote в permanent при imp≥8) → `consolidate_facts` (relations: supersedes/contradicts/confirms/related_to) → `extract_causal_links` → каждые 10 компрессов `generate_reflections` → `generate_personality_snapshot` (delta-merge с decay интересов) → `apply_importance_decay` (dormant при age>90 и imp≤4) → `analyze_retrieval_effectiveness` (boost/lower по usage) → knowledge_domains → master summary (≤2000 симв.).

**Хранилища:** SQLite (facts, messages, summaries, reflections, beliefs, embeddings, identity_facts, meta: personality/user_model/master_summary) + JSONL-файлы (goals, causal_links, predictions, world_model.json, self_model.json, self_errors) + legacy txt.

# ЭТАП 2. УТЕЧКИ ИНТЕЛЛЕКТА (главное)

### У-1. FAISS-ранжирование и mood-boost НЕ попадают в финальный промпт — критическая утечка

В `_generate_and_send_response` bundle с `faiss_scores` и `mood` собирается, но `_build_user_prompt_block` **игнорирует** параметр `retrieval_context` (комментарий в bot_core.py:746). Реально в промпт уходит контекст из `build_system_instruction` (sessions.py), где `retrieval.select()` вызывается **без faiss_scores и без mood** → семантика деградирует до keyword-overlap. Итог: вся FAISS-инфраструктура, mood-aware retrieval и dormant-revival работают вхолостую для основного ответа.

### У-2. Retrieval-метрики измеряют выброшенный контекст

`_analyze_context_utilization` считает sent/used по **невыброшенному в промпт** bundle. Затем `analyze_retrieval_effectiveness` **корректирует importance фактов** на основе этих ложных метрик. Система самообучается на мусорных данных — это хуже, чем отсутствие обучения.

### У-3. Relation «contradicts» сохраняется и умирает

Консолидация умеет находить противоречия, но `add_relation` обрабатывает только `supersedes`. Противоречия не всплывают ни в промпт, ни пользователю, ни в belief revision. Требование «обнаруживает противоречия» реализовано на 20%.

### У-4. Predictions — мёртвая подсистема

`add_prediction` не вызывается **нигде**. `captured_prediction` всегда `""`. Верификации (verified/falsified) нет. Гипотезы о будущем пользователя не формируются вообще.

### У-5. Reflections не индексируются в вектор

`add_reflection` не вызывает `compute_and_cache`, `reindex_all` намеренно пропускает reflections. Следствия: (а) FAISS-дедуп рефлексий в `generate_reflections` всегда пуст → дубликаты копятся; (б) `search_reflections(query)` всегда возвращает `[]` при наличии query.

### У-6. Beliefs пользователя не используются

`user_model.data["beliefs"]` — пустой dict навсегда (reflection-промпт не заполняет его). Beliefs из store попадают только в personality-пайплайн, но не в контекст ответа.

### У-7. Эмоциональная динамика не накапливается

Mood считается LLM на каждом сообщении и... выбрасывается (использовался только в mood-boost выброшенного bundle). Нет временного ряда настроения → «замечать изменения личности/состояния во времени» невозможно. `emotional_timeline` хранит только триггеры-списки и baseline.

### У-8. `evidence`фактов и `based_on`рефлексий никогда не читаются

Провenance записывается, но не используется ни для контекста, ни для разрешения конфликтов.

# ЭТАП 3. ПЕРСОНАЛИЗАЦИЯ

| Область | Статус
|-----|-----
| Предпочтения/интересы | **Работает частично.** Interests с decay и floor — хорошо. Но micro-update считает интересы по **хардкод-списку из 20 топиков** (bot-специфичных: «морзик», «аня») → новые интересы между компрессами невидимы; счётчики не клампятся к 10.
| Привычки | Работает через habits_delta, но только на compress (раз в 50 сообщений).
| Проекты | **Отсутствует как сущность.** Есть goals, но захват через regex «хочу…» создаёт мусорные «цели» из любой фразы («хочу пиццу» → цель priority 5). Прогресс целей не отслеживается автоматически.
| Отношения | Работает (relationships_delta + IdentityVault partner), но нет модели «кто есть кто» с историей упоминаний.
| Эмоциональные паттерны | **Слабо.** Триггеры-списки растут append-only без весов/частот/затухания; нет временного ряда (см. У-7).
| Мировоззрение | Beliefs копятся в store, но не циркулируют (У-6); belief revision отсутствует.
| Долгосрочные цели | Хранятся, но lifecycle (progress, staleness, completion detection) не автоматизирован.
| Долгосрочная непрерывность | Master summary — хорошая идея, но жёсткий cap 2000 символов означает, что через год memory-хайлайты будут вытеснять друг друга.


Отдельно: **mood_to_retrieval_boost и авто-теги anchor в pipeline.py содержат хардкод ключевых слов конкретного пользователя** («морзик», «qa», «не выпил»). Это персонализация, зашитая в код, а не выученная — она сломается при любом изменении жизни пользователя.

# ЭТАП 4. СКРЫТЫЕ БАГИ

### Б-1. Proactive loop мёртв (ImportError) — критично

`proactive/loop.py`: `from companion.bot_core import bot, bot_config` — **ни `bot`, ни `bot_config` в bot_core не существуют** (bot создаётся локально в `main.run()`). Также `from companion.llm.sessions import _resolve_strategy, _resolve_tone` — **этих функций нет в sessions.py**. Каждые 30 минут луп падает с ImportError, ловится `except Exception` и молча логируется. Проактивность не работает вообще. Вероятность: 100%. Дополнительно в `collector.py`: `get_goal_snapshot("")` возвращает `list`, а код вызывает `.strip()` → AttributeError; `"..." + recent_summaries` (str + list) → TypeError.

### Б-2. Ассистентские реплики теряются после рестарта

Ответы бота логируются с `importance=4` (bot_core.py:637), а `_reconstruct_recent_history` фильтрует `min_importance=5` → после рестарта история одностороняя (только реплики пользователя). «Ощущение непрерывности» ломается именно там, где его чинили.

### Б-3. Обрезка ответа бота до 500 символов при логировании

`text[:500]` → в episodic memory и в compress попадают огрызки ответов бота; summary строится по неполным данным.

### Б-4. Самозатирание identity через `explicit_overwrite=True`

`user_model._sync_io` пишет в IdentityVault с `explicit_overwrite=True` при **каждой** рефлексии — весь механизм IdentityLock/should_lock_update обходится. Единственная защита — shadow eval, который при ошибке LLM возвращает `True` (allow). Дрейф ядра личности возможен.

### Б-5. Двойной/тройной retrieval на каждое сообщение

`_load_retrieval_context` + `retrieval_mgr.select` + `build_system_instruction→retrieval.select` (иногда дважды: create_default_session + пересоздание). Плюс `_ranked_score` пишет `logger.info` **на каждый факт** → лог-спам и латентность.

### Б-6. `compress_and_reset`восстанавливает счётчик с гонкой

При неудаче: `user_message_counts[uid] = get(uid,0) + original_count` — сообщения, пришедшие во время компресса, суммируются с original — счётчик может перепрыгнуть порог и зациклить компрессы. Низкая вероятность, но реальна.

### Б-7. `search_facts`для dormant не вызывает `revive_dormant_fact`

Dormant-факт попадает в выдачу при score ≥ 0.80, но статус не меняется (метод revive существует, не вызывается) → факт остаётся dormant и не проходит фильтр `active` в `_load_retrieval_context.merged`-ветке. «Оживление» памяти фактически не работает.

### Б-8. Вектор-«супернова» при совпадении текстов

`vector_index` ключует по hash содержимого: два разных факта с одинаковым текстом делят embedding; `delete_for_content` при supersede может удалить вектор текста, который используется другим типом контента (summary/belief с тем же текстом) — маловероятно, но архитектурно грязно.

### Б-9. `user_chats`/`_compression_locks`/`_last_reflection_time`— утечки на многопользовательность

Всё глобальные dict'ы без очистки; для одного admin-пользователя ок, но архитектура однопользовательская по факту при многопользовательском интерфейсе.

### Б-10. Мусорный захват целей

`maybe_capture_goal` regex `хочу\s+(.+)` при importance ≥ 6 создаёт цель из любой эмоциональной фразы. Загрязняет goals → загрязняет проактивность и контекст.

# ЭТАП 5. ПАМЯТЬ — оценка по типам

- **Episodic**: есть (messages + events), но события извлекаются regex-маркерами («сегодня», «купил») — LLM-извлечение эпизодов отсутствует. Эпизоды не имеют нарратива «что было → чем кончилось».
- **Semantic**: сильнейшая часть (facts + kinds + consolidation + decay + dormant). Не хватает: разрешение противоречий (У-3), временная версионность фактов («тогда X, теперь Y» как история, а не supersede-затирание).
- **Identity**: IdentityVault + user_model — хорошо, но подрывается Б-4.
- **Autobiographical**: слабая — master summary 2000 симв. — это не автобиография. Нет «глав жизни» (chapters/epochs: «период запоя», «новая работа»), monthbook есть, но не циркулирует в retrieval.
- **Emotional**: почти отсутствует как память (У-7). Нужен mood time-series + агрегаты недель.
- **Causal**: связи извлекаются, но retrieval по keyword-overlap; `observed_count` никогда не инкрементится (повторное наблюдение той же связи создаёт дубликат вместо усиления уверенности).
- **Отсутствует полностью**: prospective memory (пользователь сказал «в пятницу у меня собеседование» → бот должен вспомнить в пятницу). Это самый высокоценный недостающий тип для «человечности».

# ЭТАП 6. REASONING

- **Выводы**: reflections — да, но раз в 10 компрессов (~500 сообщений!) — слишком редко для «замечает закономерности».
- **Гипотезы**: нет (У-4).
- **Пересмотр убеждений**: нет. Beliefs append-only с дедупом; falsifications из рефлексии логируются в JSONL и никого не трогают.
- **Причинность**: извлечение есть; рассуждение по цепочкам (`get_causal_chain`) требует **точного** совпадения строк cause/effect — на естественном языке цепочки почти никогда не строятся.
- **Замечание изменений пользователя**: `changes` в personality — список строк без анализа; ретроспектива только по команде.


**Предлагаемая архитектура** (когда дойдём до изменений): единый фоновый «Inference Cycle» после каждого compress: (1) contradiction check по relations → карточка конфликта в контекст следующего диалога; (2) hypothesis generation → Prediction с dedline; (3) prediction verification против новых фактов → калибровка model_confidence; (4) causal reinforcement: FAISS-мэтчинг новых links против старых → `observed_count += 1` вместо дубликата.

### Желательные

11. Prospective memory: extraction «будущих обязательств» с датой + проверка в proactive loop. Средняя сложность, максимальный эффект «человечности».

16. Prediction engine с self-калибровкой уверенности (У-4 + ЭТАП 6-архитектура). Высокая сложность, риск средний.
17. Belief revision: falsifications из рефлексий реально помечают beliefs как deprecated. Средняя.
18. «Narrative memory»: LLM-генерация эпизодических нарративов (завязка→развязка) вместо плоских событий. Высокая.
