# Amargon Companion Bot v2 - Полный Архитектурный Аудит
Дата генерации: 04.07.2026

Архитектура бота эволюционировала из простого LLM-перехватчика в сложную автономную систему с многоуровневой памятью, проактивностью, системой защиты идентичности и динамической политикой общения. Ниже представлено подробное описание каждого модуля и его роли в проекте.

---

## 1. Ядро оркестрации и Инициализация (Core Orchestration)
Эта подсистема отвечает за прием событий из Telegram, их маршрутизацию и управление жизненным циклом сессии.

* **`main.py`**: Точка входа приложения. Инициализирует логгер, проверяет ротацию JSONL-файлов, поднимает базу данных, запускает фоновые задачи (проактивный луп) и стартует aiogram-поллинг. Здесь же находится `AuthMiddleware`, обеспечивающая доступ к боту только по белому списку ID.
* **`bot_core.py`**: "Спинной мозг" бота. Главная функция `process_llm_request` связывает все модули воедино:
  1. Вызывает `analyzer` для понимания интента.
  2. Запрашивает контекст у `RetrievalBudgetManager`.
  3. Собирает команды и запускает `PolicyLayer`.
  4. Маршрутизирует данные в `generate_and_send_response` или выполняет команды изменения состояния (например, `/remember`).
  Также отвечает за компрессию контекста (запуск pipeline при достижении порога сообщений).
* **`background_scheduler.py`**: Запускает задачи в фоне (без блокировки Telegram-лупа). Основная задача: `background_user_model_reflection` — анализ последних диалогов для обновления модели пользователя (переоценка эмоций, паттернов).
* **`handlers/` (`chat.py`, `media.py`)**: Слой Telegram API. Прием текстовых сообщений, кнопок (inline callbacks), видео из TikTok (через `yt_dlp`). Передача полезной нагрузки в `bot_core`.
* **`runtime_state.py`**: DTO (Data Transfer Object). Описывает контекст идущего запроса (интент, настроение, найденные факты).

## 2. Подсистема Памяти и Хранения (Memory & Knowledge)
Бот использует гибридную архитектуру с несколькими типами памяти (семантическая, эпизодическая, личностная).

* **`storage/sqlite_db.py (MemoryDatabase)`**: Главный источник правды (Source of Truth). Хранит сырые факты, сообщения (историю чата), сводки (summaries), убеждения (beliefs), логи телеметрии (`proactive_events`).
* **`memory/store.py (MemoryStore)`**: Единый API/фасад над базой данных. Все остальные подсистемы (LLM, handlers) обращаются к памяти исключительно через этот класс (например, `log_message`, `add_fact`).
* **`memory/vector_index.py`**: In-memory семантический поиск. При старте бота загружает векторы (эмбеддинги) из БД в `FAISS`-индекс для моментального поиска по смыслу (cosine similarity).
* **`memory/retrieval.py (RetrievalBudgetManager)`**: Ограничитель контекстного окна. Алгоритмически отбирает релевантные факты, воспоминания и цели, укладывая их в жесткий лимит токенов для отправки в Gemini.
* **`memory/identity_vault.py (IdentityVault)`**: Защищенное хранилище идентичности самого бота. Содержит SQL-триггеры для аудита (history log). Предотвращает "дрифт" личности (когда бот от долгого общения меняет свой характер).
* **`storage/legacy.py` / `jsonl.py`**: Устаревшие методы хранения на текстовых файлах, находящиеся в процессе вывода из эксплуатации (миграция в SQLite).

## 3. Когнитивный и Аналитический слои (Cognitive & LLM)
Слой, принимающий решения и общающийся с API Gemini.

* **`llm/client.py`**: Клиент для Google Gemini API (flash, pro, embeddings). Поддерживает асинхронные вызовы, кеширование и парсинг JSON из вывода нейросети.
* **`llm/analyzer.py`**: Выполняет первую, легкую стадию LLM-анализа (оценка тона сообщения пользователя, поиск скрытых команд, важности факта).
* **`llm/shadow_eval.py`**: "Оценщик-тень". При попытке изменить идентичность бота или юзера, независимый вызов LLM проверяет, не является ли это изменение галлюцинацией или опасным дрифтом, и блокирует его.
* **`llm/pipeline.py` & `sessions.py`**: Управление контекстом. Когда в чате скапливается много сообщений, запускается `run_compress_pipeline`, который "схлопывает" старые переписки в краткие summaries.
* **`reasoning.py` / `services/reasoning_service.py`**: Модуль "модели мира" и каузальных связей (понимание причин и следствий). Хранит предсказания и цели пользователя (в данный момент на базе JSON, ожидает миграции в SQLite).

---

## 4. Модель пользователя и Динамическая политика (User Model & Policy)
Система, превращающая бота в эмпатичного компаньона.

* **`user_model.py (UserModel)`**: Цифровой двойник пользователя. Хранит информацию о страхах, ценностях, паттернах поведения и копинг-стратегиях. Каждые несколько сообщений бот запускает фоновую LLM-рефлексию (`reflect_after_interaction`) для обновления этого профиля.
* **`policy_layer.py` (Policy Engine V6)**: Жесткий детерминированный движок, который накладывает ограничения на генерацию ответа. Если `user_model` сообщает, что у пользователя состояние "anxious" (тревожность), политика автоматически переводит бота в режим `anchor` (заземление, отказ от конфронтации, короткие спокойные ответы), подмешивая соответствующие инструкции (Strategy и Tone) в финальный промпт.

---

## 5. Умная проактивность (Proactive Loop)
Подсистема самостоятельной инициативы бота. Архитектура построена как линейный конвейер.

* **`proactive/loop.py`**: Оркестратор. Запускается по таймеру и прогоняет конвейер.
* **`proactive/engagement.py` (Engagement Gate)**: Жестко рубит спам. Проверяет cooldown (не чаще раза в 12ч), время тишины юзера (не трогать, если писал недавно), счетчик игноров (отстать, если юзер не ответил на 3 прошлых пинга).
* **`proactive/reasons.py` (Reason Selector)**: Математический выбор причины (долгое молчание, эмоциональный чекап, недоделанная цель).
* **`proactive/collector.py`**: Сборщик фактов. Дает LLM только те данные, которые касаются выбранной причины, снижая шанс бреда.
* **`proactive/formatter.py`**: "Тупой рендерер". Строго генерирует одно короткое сообщение без галлюцинаций.
* **`proactive/telemetry.py`**: Пишет логи в базу (кто, когда и почему был пинганут, ответил ли юзер) для аналитики.

---

## 6. Текущий Roadmap (Планы развития и технический долг)

1. **Мониторинг телеметрии Proactive Loop (Current Focus):** Ожидание накопления данных за 5-7 дней для корректировки Engagement Gate и анализа Reply Rate.
2. **Shared Lore (Phase 0 & 1):** Создание общего хранилища "локальных мемов" и внутренних шуток между ботом и юзером. Сейчас реализована Фаза 0 — скрытый сбор кандидатов (`shared_lore_candidates.jsonl`) для оценки качества алгоритма перед внедрением в базу.
3. **Полная миграция Reasoning в SQLite:** Отказ от разрозненных JSON/JSONL-файлов для хранения каузальных связей, целей и предсказаний пользователя. Все переедет в `sqlite_db.py` для транзакционной целостности.
4. **Устранение дубликатов идентичности (Identity Consolidation):** Сейчас профиль личности частично "размазан" между `UserModel`, мета-таблицей SQLite и `IdentityVault`. Планируется свести всё к единому Source of Truth.
5. **Оптимизация реиндексации (FAISS):** Вместо пересборки всех векторов в памяти при каждом запуске бота (`reindex_all`), планируется механизм кэширования и хеширования.
6. **Очистка _compression_locks:** Добавление механизма удаления `asyncio.Lock` в памяти после завершения компрессии сессии во избежание микро-утечек RAM.
7. **Удаление legacy:** Финальный отказ от `storage/legacy.py` после завершения переноса всех старых заметок и туду-листов в SQLite.
