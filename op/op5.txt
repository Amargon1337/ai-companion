  1. Executive Summary

  Архитектура жизнеспособна. Перепроектирование не требуется. Границы слоёв проведены правильно и — что редкость —
  соблюдаются: в companion/memory/ и companion/storage/ ноль импортов aiogram или bot_core. Memory layer физически не
  знает о Telegram. Это главный актив проекта, и он снимает вопрос о «переписать с нуля».

  Production-capable — нет, пока не закрыты P0. Не из-за архитектуры, а из-за конкретных дефектов: одна функция памяти
  падает на каждом вызове в проде и не ловится тестами, схема БД не версионирована, а таблица аудита растёт без
  ограничений (5.7 MB архива против 456 KB самой базы).

  Точный диагноз: прочный скелет, ненадёжная эксплуатационная обвязка. Проблемы — точечные и дешёвые в исправлении, ни
  одна не требует смены дизайна.

  Source of truth — SQLite, и это соблюдено. faiss_index.bin — производный кэш; при расхождении он перестраивается из
  БД, а не наоборот.

  Механизм консистентности лучше, чем ожидалось, — отдаю должное:
  - _mark_dirty (:283) ставит флаг faiss_index_dirty=1 внутри той же транзакции, что и запись эмбеддинга.
  - При старте _load_index (:239-251): если флаг взведён — индекс с диска игнорируется и делается полный
  _rebuild_index() из SQLite.
  - remove_ids на HNSW обёрнут в try/except с фолбэком на полную перестройку (:767-772) — редкий случай, когда
  ограничение HNSW действительно учтено.

  То есть kill -9 не приводит к тихому рассогласованию — при следующем старте индекс восстановится. Это сознательно
  спроектированный crash-recovery.

  Что реально остаётся дырой:
  1. Перестройка стоит полного прохода по эмбеддинг-API. При embeddings_enabled = False (взводится в main.py:211-212 при
  неудачном тесте) rebuild даст пустой индекс — retrieval молча выродится в BM25/пустоту.
  2. Между коммитом факта и FAISS-add (upsert_embedding:401-416, вне with self._conn()) окно есть, но dirty-флаг его
  закрывает при рестарте.
  3. Расхождение диск/БД уже наблюдаемо: faiss_index.bin — 271 байт при 76 KB маппинга в JSON.

  Минимальные изменения (без переписывания FAISS):
  - Удалить мёртвую таблицу faiss_mapping и 4 метода при ней, либо — если планировалась как замена state_models —
  довести до использования. Сейчас это ловушка для следующего инженера.
  - Переместить data/faiss_mapping.json в data/legacy/ после подтверждения миграции.
  - Добавить проверку размерности при загрузке индекса (сейчас смена EMBEDDING_DIM даст молчаливый мусор).
  - Логировать WARNING, если rebuild отработал при выключенных эмбеддингах.

  5. Memory Architecture Review

  Уверенность средняя: агент по lifecycle упал, полный перечень состояний не обойдён.

  Подтверждено:
  - Facts — ядро, OCC-колонка version, статусы active/superseded/inactive/archived/dormant/pending_review
  (models.py:10).
  - Beliefs — content-hash ID (sqlite_db.py:789), единственное место с детерминированным идентификатором.
  - Reflections / Patterns — version есть, но update_pattern_fields:1439-1450 его не инкрементирует, хотя пишет
  updated_at.
  - Dedup — опирается не на storage, а на вектор: store.py:222 find_similar_fact_any_status. models._new_id (:25-26)
  содержит uuid4, поэтому ON CONFLICT(id) при повторной попытке ингеста не сработает — родится дубль.
  - Persistence guarantees — atomic_memory_transaction существует (:112), но имеет ровно один вызов: persistence.py:55.
  Остальные многошаговые операции неатомарны.

  Может ли память деградировать, потеряться или стать противоречивой — да, тремя путями:

  1. Противоречивость — реально. OCC отключён на главном пути записи (store.update_fact без expected_version), а
  increment_fact_usage и record_fact_access_batch меняют строку вообще без версии. Колонка version не отражает все
  изменения, поэтому как токен конкурентности она уже несостоятельна.
  2. Дубликаты — реально. Не-контентные ID + дедуп через вектор: при выключенных эмбеддингах дедуп исчезает целиком.
  3. Потеря — ограниченная. Полной потери фактов не нашёл: _insert_fact использует ON CONFLICT ... DO UPDATE с COALESCE,
  delete_fact атомарен, GC по GC.md только архивирует. Теряются периферийные вещи: Fact.entity_ids объявлен
  (models.py:57), сериализуется в to_dict, но колонки под него нет — значение исчезает при каждой записи.

  Итог: катастрофической потери памяти архитектура не допускает; тихая деградация качества — допускает.

  Final Verdict

  Архитектура фундаментально жизнеспособна. Перепроектирование не нужно и было бы ошибкой.

  Обоснование, а не комплимент: правильно решена самая дорогая для исправления вещь — разделение слоёв. Memory layer не
  импортирует Telegram; storage изолирован; LLM-вызовы проходят через одну функцию run_llm. Это то, что при неудаче
  требует переписывания, и это сделано верно. Плюс есть неочевидно грамотные решения — dirty-флаг FAISS внутри
  транзакции, фолбэк remove_ids для HNSW, circuit breaker, версионные колонки.

  Критическая часть: система выглядит надёжнее, чем есть. Инфраструктура целостности построена, но не подключена — OCC
  написан и не обрабатывается, atomic_memory_transaction написан и вызывается один раз, archive_audit_log написан и не
  вызывается никогда. Это паттерн «защита реализована, но не активирована», и он опаснее её отсутствия, потому что
  создаёт ложную уверенность. Ровно то же с тестами: 255 зелёных при функции, падающей на каждом вызове в проде.

  Практический вывод: Phase 0 — это порядка дня работы, после чего систему можно эксплуатировать. Phase 1 переводит
  существующие гарантии из декларативных в фактические. Ни один пункт не требует смены дизайна — все находки локальны.

  Код не менял, файлы не создавал. Готов реализовать Phase 0 после утверждения — или сначала углубить непроверенные зоны
  (lifecycle-состояния и полный учёт LLM-вызовов), где упавшие агенты оставили пробел.
