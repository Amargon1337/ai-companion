```mermaid

    autonumber
    actor User as Telegram User
```

1. **Lifecycle of a User Message**:
   - Received by `aiogram` router in `chat.py` -> input sanitized -> queries `MemoryStore.search_memories()` -> prompt block generated -> sent to `LLMClient.generate_text()` -> reply sent to user -> raw exchange passed asynchronously to memory capture.
2. **Lifecycle of a Memory Item (Fact)**:
   - Extracted from interaction -> scored for initial importance (`importance.py`) -> vectorized via `LLMClient.extract_embeddings()` -> added to SQLite (`Fact` table) and FAISS index (`VectorIndex`) -> subject to exponential/hyperbolic time-decay during retrieval -> updated or superseded during factual deduplication.
3. **Lifecycle of a Reflection**:
   - Synthesized during sleep/background consolidation (`companion/proactive/subconscious.py` or `llm/pipeline.generate_reflections()`) from clusters of related facts -> stored in SQLite `reflections` table -> indexed in FAISS -> retrieved during high-level thematic queries -> pruned if contradicted by newer reflections.
4. **Lifecycle of a Belief (`UserModel`)**:
   - Derived by `UserModel.reflect_after_interaction()` -> captures enduring user personality traits, preferences, and emotional baselines -> stored in SQLite `user_beliefs` table -> injected into system prompts via `UserModel.to_prompt_block()` -> updated continuously to control persona drift.
5. **Lifecycle of a Prediction (Prospective Memory)**:
   - Evaluated by `companion/proactive/prospective.py` -> extracts future commitments or scheduled check-ins -> stored as a scheduled task or prediction in SQLite -> polled by `proactive_ping_loop()` -> triggers a proactive message when timestamp arrives.

## 8. RISKS, BOTTLENECKS & HIDDEN TECHNICAL DEBT

### A. Performance & Bottlenecks
1. **SQLite Concurrency & Lock Contention (`database is locked`)**:
   - `MemoryDatabase` relies on standard Python `sqlite3` connections. While SQLite Write-Ahead Logging (WAL) is enabled, concurrent asynchronous writes from Telegram message ingestion, proactive background loops, and background memory consolidation risk hitting `OperationalError: database is locked` under multi-user or high-velocity interaction spikes.
2. **FAISS CPU Index Serialization Bottlenecks**:
   - `VectorIndex` runs on `faiss-cpu`. Adding vectors is fast in memory, but saving the index to disk requires serializing the entire FAISS index structure. As factual memories scale into tens of thousands of vectors, synchronous disk I/O on index updates will degrade message response latency.
3. **Token Usage & Context Budgeting Bottlenecks**:
   - During retrieval (`retrieval.py`), prompt assembly concatenates top-K facts, reflections, identity vault items, and user beliefs. If a user has a long conversation history, uncalibrated token budget estimation can either truncate critical context or trigger API Rate Limit / Token Expiry errors on smaller context models (e.g., Gemma / Gemini Flash).

### B. Scalability & Concurrency Risks
- **Single-Node In-Memory State**: The FAISS index and SQLite database are bound to a single local filesystem path (`C:\Users\Ivan\.gemini\antigravity\...`). The architecture cannot be horizontally scaled across multiple worker pods without migrating to a distributed client-server vector database (e.g., Qdrant, Milvus, or pgvector) and an enterprise relational database (PostgreSQL).
- **Asyncio Event Loop Blocking**: CPU-bound operations—such as FAISS similarity search, embedding normalization, and JSON parsing of large memory blocks—are executed within the main `asyncio` event loop. Under load, this can stall Telegram heartbeat pings and cause webhook timeouts.

### C. Maintainability, Extensibility & Hidden Technical Debt
1. **Tight Coupling of Storage to Domain Evolution**:
   - Adding any new cognitive capability (e.g., "Episodic Memory" or "Emotional Arc Tracking") requires modifying 5 distinct layers sequentially: `models.py` (dataclass) -> `sqlite_db.py` (DDL & SQL queries) -> `store.py` (façade wrappers) -> `retrieval.py` (ranking weight) -> `pipeline.py` (LLM prompt).
2. **Hidden Technical Debt in Error Resilience**:
   - LLM API failures (timeouts, quota limits) during background consolidation or proactive pinging can fail silently or log generic warnings without transactional rollback of partial database writes, leading to state drift between the SQLite factual database and the FAISS vector index.

## 2. DETAILED ARCHITECTURAL FINDINGS BY CATEGORY

### A. SOLID, SRP & DEPENDENCY INVERSION VIOLATIONS

#### 1. SRP & OCP Violation: `MemoryDatabase` as a Monolithic Storage God Object
- **Severity**: **HIGH (Sev 2)**
- **Domain**: Single Responsibility Principle (SRP) / Open-Closed Principle (OCP)
- **Root Cause**: `companion/storage/sqlite_db.py` (`MemoryDatabase`) contains **117 methods** within a single class. It handles schema creation, migrations from JSONL, DDL management, transaction control, row-to-dataclass hydration, and CRUD operations for **12 distinct domain entities** (`facts`, `reflections`, `user_beliefs`, `messages`, `goals`, `causal_links`, `prospective_tasks`, `system_logs`, etc.).
- **Impact**: Any change to a single entity (e.g., adding a column to `Fact`) forces modification of this monolithic class, violating OCP and creating merge conflicts across concurrent feature branches.
- **Cost**: **Medium** (~3–5 days to refactor into modular repositories: `FactRepository`, `ReflectionRepository`, `BeliefRepository` sharing a common `SqliteConnectionPool`).

#### 2. SRP Violation: `MemoryStore` as an Indiscriminate Façade
- **Severity**: **HIGH (Sev 2)**
- **Domain**: Single Responsibility Principle (SRP)
- **Root Cause**: `companion/memory/store.py` (`MemoryStore`) has a degree of **134 (60 In / 74 Out)**. It acts as an omnibus façade coupling factual retrieval, vector indexing, identity vault, semantic ranking, and reflection distillation into a single class.
- **Impact**: High vertical coupling; callers cannot interact with specific subsystems (e.g., identity vault or vector index) without importing and initializing the entire `MemoryStore` heavyweight dependency.
- **Cost**: **Medium** (~3 days to segregate interfaces via Interface Segregation Principle: `IFactStore`, `IVectorStore`, `IIdentityVault`).

#### 3. Dependency Inversion Violation (DIP): Concrete SQLite / FAISS Dependency in Core Logic
- **Severity**: **MEDIUM (Sev 3)**
- **Domain**: Dependency Inversion Principle (DIP)
- **Root Cause**: High-level modules (`companion/proactive/subconscious.py`, `companion/llm/pipeline.py`, `companion/user_model.py`) instantiate or directly call concrete implementation classes (`MemoryStore`, `MemoryDatabase`, `VectorIndex`) rather than depending on abstract base classes or protocols (`typing.Protocol`).
- **Impact**: Impossible to unit-test cognitive pipelines or swap storage engines (e.g., PostgreSQL + pgvector or Qdrant) without monkeypatching or editing core application logic.
- **Cost**: **Low–Medium** (~2 days to define Python `Protocol` definitions for storage and retrieval contracts).

#### 4. Abstraction Leaks: Raw SQL Tuples & Dict Hydration Leaking into Pipelines
- **Severity**: **MEDIUM (Sev 3)**
- **Domain**: Abstraction Integrity
- **Root Cause**: While `companion/models.py` defines clean dataclasses (`Fact`, `Reflection`), several internal methods in `MemoryDatabase` and `MemoryStore` accept raw dictionaries or pass SQL tuples/dicts directly to formatting layers (`formatter.py`, `retrieval.py`).
- **Impact**: Type safety is lost across module boundaries; refactoring a dataclass field name does not generate compile/lint errors in downstream formatting dictionaries.
- **Cost**: **Low** (~1–2 days to enforce strict dataclass boundary serialization via Pydantic or `dataclasses.asdict` wrappers).

---

### B. STRUCTURAL DESIGN: COMPLEXITY & ENGINEERING BALANCE

#### 5. Over-Engineering: Multi-Layered Wrapper Boilerplate in Factual Retrieval
- **Severity**: **LOW (Sev 4)**
- **Domain**: Over-Engineering / Unnecessary Complexity
- **Root Cause**: Adding a single parameter to a search query requires touching `MemoryStore.search_memories()`, `RetrievalEngine.retrieve_relevant_memories()`, `SemanticRanker.rank()`, and `VectorIndex.search()`.
- **Impact**: High cognitive overhead for developers; simple features require boilerplate passthrough arguments across 4 layers.
- **Cost**: **Low** (~1 day to consolidate `RetrievalEngine` and `SemanticRanker` into a cohesive pipeline).

#### 6. Under-Engineering: Fragmented Background Task Supervision
- **Severity**: **MEDIUM (Sev 3)**
- **Domain**: Under-Engineering
- **Root Cause**: Background tasks (`proactive_ping_loop` in `proactive/loop.py`, `background_user_model_reflection` in `background_scheduler.py`, and `run_subconscious_consolidation`) are spawned as isolated `asyncio.create_task()` background jobs without a centralized supervisor, circuit breaker, or exponential backoff retry state machine.
- **Impact**: If an unhandled exception occurs in a background loop, the loop terminates silently, permanently halting proactive pings or sleep consolidation for the remainder of the bot's uptime.
- **Cost**: **Medium** (~2–3 days to implement a unified `SupervisorService` with health monitoring and restart policies).

---

### C. CONCURRENCY, SYNCHRONIZATION & RACE CONDITIONS

#### 7. CRITICAL: SQLite Asynchronous Lock Contention (`OperationalError: database is locked`)
- **Severity**: **CRITICAL (Sev 1)**
- **Domain**: Concurrency & Synchronization
- **Root Cause**: `MemoryDatabase` uses synchronous `sqlite3` connections wrapped in `asyncio.to_thread()` or direct calls. SQLite in WAL mode permits concurrent reads, but **only one write transaction at a time**. Concurrent writes from Telegram user messages, proactive pings, and background consolidation will collide, throwing `sqlite3.OperationalError: database is locked`.
- **Impact**: Dropped user messages, failed memory persistence, and unhandled 500-level bot crashes during concurrent interaction spikes.
- **Cost**: **Medium** (~2 days to implement an asynchronous write-serializer queue / `asyncio.Lock` around SQLite write transactions or migrate to `aiosqlite` with a dedicated writer worker).

#### 8. CRITICAL: State Race Condition Between FAISS In-Memory Index and SQLite
- **Severity**: **CRITICAL (Sev 1)**
- **Domain**: Distributed/Dual-Store Consistency
- **Root Cause**: When adding a fact (`MemoryStore.add_fact`), the system writes to SQLite (`_insert_fact`) and appends the vector to the FAISS in-memory index (`VectorIndex.add`). This is **not an atomic two-phase commit**. If the process crashes or an exception occurs after FAISS insertion but before SQLite commit (or vice versa), the vector index ID mapping becomes permanently desynchronized from SQLite primary keys.
- **Impact**: Vector search returns incorrect fact IDs or `IndexError` during metadata hydration, corrupting long-term memory retrieval.
- **Cost**: **Medium** (~2 days to implement a write-ahead transaction log or rebuild FAISS index IDs deterministically from SQLite during startup/recovery).

#### 9. High-Risk: Thread-Safety Violation in `FAISS` Vector Index
- **Severity**: **HIGH (Sev 2)**
- **Domain**: Thread Synchronization
- **Root Cause**: `faiss.IndexFlatIP` / `faiss.IndexFlatL2` in `VectorIndex` is accessed concurrently by async read queries (`search_memories`) and background write additions (`add_fact`) without a `threading.Lock` or `asyncio.Lock`. FAISS CPU indices are not inherently thread-safe during concurrent modification.
- **Impact**: Segmentation faults (`SIGSEGV`) in the C++ FAISS runtime or corrupted internal inverted lists.
- **Cost**: **Low** (~0.5 days to wrap `VectorIndex` read/add/save operations in an `asyncio.Lock`).

---

### D. SCALABILITY, PERFORMANCE & RESOURCE INEFFICIENCIES

#### 10. CRITICAL: FAISS Full-Index Disk Serialization Blocking I/O
- **Severity**: **CRITICAL (Sev 1)**
- **Domain**: FAISS Inefficiency / I/O Blocking
- **Root Cause**: `VectorIndex.save()` writes the entire FAISS index structure to disk (`.faiss` file) synchronously. As the index grows to 50,000+ vectors, disk serialization takes hundreds of milliseconds, blocking the main Python thread.
- **Impact**: Severe latency spikes on Telegram message handling every time a new memory is persisted and serialized.
- **Cost**: **Medium** (~2 days to decouple disk persistence into a debounced background thread or use an incremental vector log).

#### 11. HIGH: Unbounded In-Memory Loading of All Factual Vectors
- **Severity**: **HIGH (Sev 2)**
- **Domain**: Scalability Limitation / Memory Leaks
- **Root Cause**: The entire FAISS vector index resides permanently in RAM. There is no partitioning by user ID or memory tier (e.g., hot vs. cold memory). In a multi-user deployment, memory consumption grows linearly without bound ($O(N)$ RAM where $N$ is total facts across all users).
- **Impact**: Out-Of-Memory (OOM) crashes on standard VPS containers (e.g., 2GB–4GB RAM limits) as the database accumulates historical facts.
- **Cost**: **High** (~4–5 days to implement user-scoped FAISS indexes or migrate to an out-of-core vector store like Qdrant/SQLite-vss).

#### 12. HIGH: $O(N)$ Factual Deduplication & Python-Side Table Scanning
- **Severity**: **HIGH (Sev 2)**
- **Domain**: SQLite Inefficiency / Unnecessary Complexity
- **Root Cause**: Factual deduplication and semantic similarity checks often retrieve large batches of fact metadata from SQLite into Python lists to perform filtering, time-decay score recalculation, and string similarity matching in user space.
- **Impact**: High CPU utilization and unnecessary Python garbage collection allocations (`Unnecessary Allocations`) on every memory search.
- **Cost**: **Medium** (~2 days to push mathematical decay scoring and filtering into SQL queries using SQLite user-defined functions or SQL index optimizations).

#### 13. MEDIUM: Token Budget Inefficiency in `RetrievalBudgetManager`
- **Severity**: **MEDIUM (Sev 3)**
- **Domain**: Retrieval & Token Inefficiency
- **Root Cause**: `RetrievalBudgetManager` estimates token usage using character-count division heuristics (`len(text) // 4`) rather than exact tokenizer encodings (`tiktoken` or sentencepiece).
- **Impact**: Either wastes 15–20% of available LLM context window (under-utilization) or exceeds context limits on dense Cyrillic/Unicode prompts (triggering API 400 errors).
- **Cost**: **Low** (~1 day to integrate an exact token-counting cache or model-specific tokenizer).

#### 14. MEDIUM: Unindexed SQLite Foreign Key & Temporal Range Queries
- **Severity**: **MEDIUM (Sev 3)**
- **Domain**: SQLite Inefficiency
- **Root Cause**: Queries filtering by `created_at`, `importance`, or `user_id` across `facts`, `reflections`, and `user_beliefs` lack composite covering indexes in `_init_schema`.
- **Impact**: SQLite performs full table scans on historical lookups, degrading query speed from $O(\log N)$ to $O(N)$ as history grows.
- **Cost**: **Low** (~0.5 days to add composite DDL `CREATE INDEX` statements for `(user_id, created_at)` and `(user_id, importance)`).

## 3. MAJOR RELEASE 1: v2.0 — "HARDENED CORE & CONCURRENCY SAFETY"

> **Theme**: Eliminate Sev-1 critical operational risks (SQLite locks, FAISS thread crashes, atomic desynchronization) and push mathematical operations into the SQL engine.

### 3.1 Feature 2.1: Dual-Store Atomic WAL Log (FAISS / SQLite Synchronization)
- **Why it is needed**: Currently, writing a fact inserts into SQLite and appends to FAISS RAM sequentially. If a crash occurs between the two steps, the vector index ID mapping permanently desynchronizes from database primary keys.
- **Architectural Impact**: Introduces an intermediate **Write-Ahead Vector Log (`vector_wal`)** table in SQLite. Vectors are written to the SQLite log transactionally alongside the factual record before being projected into the FAISS index in memory.
- **Migration Strategy**:
  1. Add `vector_wal` table via a forward-only schema migration in `_init_schema()`.
  2. Implement a startup bootstrapper that checks `vector_wal` on launch and replays any uncommitted vectors into FAISS.
- **Backward Compatibility**: Fully backward compatible. Existing SQLite tables and `.faiss` index files remain valid; the WAL table simply acts as an atomic staging area.
- **Implementation Complexity**: **Low–Medium** (~2 days).
- **Risks**: Slightly increased SQLite storage size due to storing temporary BLOB vectors in `vector_wal` before checkpoint pruning.

### 3.2 Feature 2.2: Asynchronous SQLite Write Serializer & Composite DDL Indexing
- **Why it is needed**: Under heavy Telegram traffic or proactive check-ins, concurrent synchronous SQLite writes collide, causing `sqlite3.OperationalError: database is locked`. Furthermore, queries filtering by `(user_id, created_at)` perform full table scans.
- **Architectural Impact**: 
  - Wraps all write transactions in a singleton `asyncio.Lock` writer queue within `MemoryDatabase`.
  - Injects covering composite indexes (`idx_facts_user_created`, `idx_reflections_user_created`) into the database DDL.
- **Migration Strategy**: Execute an idempotent migration script on startup: `CREATE INDEX IF NOT EXISTS ...` across all historical databases.
- **Backward Compatibility**: 100% backward compatible. No API changes to `MemoryStore` or callers.
- **Implementation Complexity**: **Low** (~2 days).
- **Risks**: Zero functional risk; eliminates database lock timeouts and speeds up historical lookups by 10$\times$–50$\times$.

### 3.3 Feature 2.3: Debounced Asynchronous FAISS Disk Serialization
- **Why it is needed**: `VectorIndex.save()` writes the entire index (`.faiss`) to disk synchronously on the main Python thread, blocking Telegram heartbeats for hundreds of milliseconds as vector counts grow.
- **Architectural Impact**: Decouples index serialization from the write request. Memory additions mark the index as `dirty`. A dedicated asynchronous background worker serializes the index to disk via `asyncio.to_thread()` on a configurable debounce timer (e.g., maximum once every 30 seconds).
- **Migration Strategy**: Replace direct `.save()` invocations in `MemoryStore.add_fact()` with `.mark_dirty()`.
- **Backward Compatibility**: 100% backward compatible with existing `.faiss` files.
- **Implementation Complexity**: **Medium** (~2 days).
- **Risks**: In the event of a sudden OS power loss, up to 30 seconds of FAISS index additions could be lost from disk—however, **Feature 2.1 (Dual-Store WAL)** automatically restores them from SQLite on restart.

### 3.4 Feature 2.4: SQL-Side Mathematical Decay Engine
- **Why it is needed**: Currently, factual deduplication and time-decay scoring retrieve large batches of SQLite rows into Python lists to calculate exponential decay in user space, wasting CPU and RAM.
- **Architectural Impact**: Registers SQLite User-Defined Functions (UDFs) via `conn.create_function("exp_decay", ...)` or translates decay formulas into native SQL mathematical queries (`importance * EXP(-0.01 * (strftime('%s','now') - created_at)/86400)`).
- **Migration Strategy**: Replace Python-side list filtering in `MemoryDatabase.search_facts_by_ids()` with parameterized SQL predicates.
- **Backward Compatibility**: 100% backward compatible.
- **Implementation Complexity**: **Medium** (~2 days).
- **Risks**: SQLite UDFs run inside the database connection lock; queries must be benchmarked to ensure mathematical execution in C/SQLite is faster than Python space.

### 4.1 Feature 3.1: Repository Pattern & SOLID Segregation of MemoryDatabase
- **Why it is needed**: `MemoryDatabase` (117 methods) violates SRP and OCP, creating high maintenance friction.
- **Architectural Impact**: Deconstructs `companion/storage/sqlite_db.py` into cohesive domain repositories:
  - `FactRepository`, `ReflectionRepository`, `BeliefRepository`, `TaskRepository`, and `SystemLogRepository`.
  - All repositories share a common asynchronous `aiosqlite` connection manager.
- **Migration Strategy**: 
  1. Implement new repositories alongside `MemoryDatabase`.
  2. Refactor `MemoryStore` to delegate to specific repositories.
  3. Deprecate and remove the monolithic `MemoryDatabase` class.
- **Backward Compatibility**: Internal refactoring; existing database schema and filenames (`memory.db`) remain untouched.
- **Implementation Complexity**: **High** (~4–5 days).
- **Risks**: Potential regression during refactoring of complex SQL queries; requires 100% unit test coverage verification before cutover.

### 4.2 Feature 3.2: ISP Protocol Façades for MemoryStore
- **Why it is needed**: `MemoryStore` is an indiscriminate 134-degree hub. Callers are forced to depend on the entire memory kernel even when only needing user identity or beliefs.
- **Architectural Impact**: Defines Python `typing.Protocol` contracts: `IFactStore`, `IReflectionStore`, `IBeliefStore`, `IVaultStore`. High-level cognitive pipelines (`proactive/`, `llm/pipeline.py`) depend strictly on the minimal protocol required for their responsibility.
- **Migration Strategy**: Implement protocols in `companion/memory/protocols.py` and update module constructors to type-hint against protocols rather than concrete classes.
- **Backward Compatibility**: 100% backward compatible.
- **Implementation Complexity**: **Medium** (~3 days).
- **Risks**: Low risk; improves IDE type checking and enables seamless mock testing.

### 4.3 Feature 3.3: Out-of-Core HNSW Vector Engine (SQLite-vss / Qdrant Embedded)
- **Why it is needed**: `faiss.IndexFlatIP` stores all vectors permanently in RAM ($O(N)$ footprint), causing Out-Of-Memory (OOM) server crashes as historical data grows.
- **Architectural Impact**: Replaces in-memory flat FAISS arrays with an out-of-core Hierarchical Navigable Small World (HNSW) vector engine—either **SQLite-vss** (vector search natively inside SQLite) or **Qdrant Embedded** (local Rust-based out-of-core vector store).
- **Migration Strategy**:
  1. Build an offline migration script `scripts/migrate_faiss_to_hnsw.py` that reads `.faiss` vectors and inserts them into the HNSW store.
  2. Swap `VectorIndex` implementation behind an `IVectorEngine` protocol.
- **Backward Compatibility**: Breaking change for binary `.faiss` disk formats; requires running the one-time migration script during deployment upgrade.
- **Implementation Complexity**: **High** (~5 days).
- **Risks**: Requires external native library binaries (`sqlite-vss` C++ extension or Qdrant Rust engine); Docker container builds must be updated.

### 4.4 Feature 3.4: Central Async `SupervisorService` for Proactive & Cognitive Loops
- **Why it is needed**: Unmonitored `asyncio.create_task()` background jobs terminate permanently if an unhandled API or DB exception occurs.
- **Architectural Impact**: Implements a dedicated `companion/supervisor.py` kernel service that manages all background lifecycles (`proactive_ping_loop`, `subconscious_consolidation`, `user_model_reflection`). Provides exponential backoff retries, circuit breakers for LLM API outages, and structured crash logging.
- **Migration Strategy**: Wrap existing loop functions in supervisor worker delegates inside `companion/bot_core.py`.
- **Backward Compatibility**: 100% backward compatible.
- **Implementation Complexity**: **Medium** (~3 days).
- **Risks**: Zero risk; drastically increases bot uptime and resilience.

### 5.1 Feature 4.1: Graph-RAG Neuro-Symbolic Knowledge Graph
- **Why it is needed**: Semantic vector search retrieves facts by cosine word similarity but fails at multi-hop reasoning (e.g., *"What did I say about my brother's new job three months ago?"* where "brother" = "Alex").
- **Architectural Impact**: 
  - Expands `companion/models.py` `FactRelation` into a true **Directed Knowledge Graph**.
  - Integrates an internal Graph-RAG engine where facts are nodes and causal/relational links (`IS_BROTHER_OF`, `WORKS_AT`, `HAPPENED_BEFORE`) are explicit directed edges.
  - During retrieval, `RetrievalEngine` performs a hybrid search: **Vector Similarity (Top-K) + N-Hop Graph Traversal** around matching entity nodes.
- **Migration Strategy**:
  1. Introduce a graph schema table (`knowledge_graph_edges`) in SQLite.
  2. Implement an offline background LLM job that traverses existing factual rows and extracts entity-relationship triples to populate the graph.
- **Backward Compatibility**: Fully backward compatible with factual queries; enhances retrieval depth automatically.
- **Implementation Complexity**: **Very High** (~7–10 days).
- **Risks**: Graph traversal can explode context window token budgets if hop-depth $N > 2$; requires strict pruning and subgraph summarization.

### 5.2 Feature 4.2: Episodic Temporal Memory & Conversational Arcs
- **Why it is needed**: The companion currently stores individual facts or abstract reflections, but lacks "Episodic Memory"—the ability to remember complete conversational narratives or temporal events in sequence.
- **Architectural Impact**: Introduces an **Episodic Arc Engine** (`companion/memory/episodic.py`). Instead of storing standalone messages, dialogue is segmented into thematic episodes (e.g., *"Planning the Japan Trip - Oct 2026"*). Episodes summarize start/end timestamps, emotional trajectory, and key decisions.
- **Migration Strategy**: Deploy alongside existing factual memory as a parallel Tier-2 retrieval index.
- **Backward Compatibility**: 100% backward compatible.
- **Implementation Complexity**: **High** (~5 days).
- **Risks**: Requires fine-tuned LLM consolidation prompts to prevent episodic summaries from losing granular details.

### 5.3 Feature 4.3: Multi-Agent Cognitive Orchestrator
- **Why it is needed**: Monolithic LLM prompts (`pipeline.py`) that attempt to simultaneously answer user queries, adhere to beliefs, check identity vaults, and format tone often suffer from attention degradation and hallucination on complex tasks.
- **Architectural Impact**: Replaces the single-pass LLM pipeline with a **Multi-Agent Cognitive Orchestrator**:
  - **Factual/Graph Agent**: Responsible exclusively for querying the Graph-RAG engine and verifying factual accuracy.
  - **Episodic/Empathy Agent**: Queries user beliefs and episodic narrative arcs to ensure emotional resonance and persona continuity.
  - **Synthesis Supervisor**: Combines agent outputs into a unified, highly contextualized natural language response.
- **Migration Strategy**: Build the agent orchestrator behind the `LLMClient` interface; allow feature-flagging between single-pass and multi-agent synthesis in `config.py`.
- **Backward Compatibility**: Fully backward compatible at the application/Telegram handler layer.
- **Implementation Complexity**: **Very High** (~8 days).
- **Risks**: Multi-agent orchestration increases API call latency and token costs by 2$\times$–3$\times$; requires concurrent async execution of subagents and fast small-model backends (e.g., Gemini Flash) for intermediate research steps.

B. Repository First Mandate
